## Requirement changes

| ID | Original requirement (P4A) | Revised requirement (P4B) | Why it changed |
| --- | --- | --- | --- |
| R1 | If the peer takes the message but never replies, the call fails with a timeout error after the deadline, and the remote task is cancelled so the peer stops working on it too. | Same, but the task is cancelled when the peer told us its id. The deadline check is "no earlier than timeoutMs and within 1 second after". | Feasibility. A streaming peer that opens the stream and never writes anything never sends a task id, so there is nothing we can cancel on its side. Users still get what they asked for, the call never stalls. The "within 2 seconds" bound was also turned into a bound relative to the deadline so it can be checked for any deadline. |
| R2 | Adding a peer and then removing it must leave the config file exactly as it was before. | Same for every file that has no allowedPeers key or a non-empty one. A hand-written empty `"allowedPeers": {}` is dropped when its last peer is removed, and a bare `"plugin-a2a"` string entry is turned into a `["plugin-a2a", {...}]` entry on the first add. | Found in Step 3. The file only stores the peers, so after removing the last peer the code cannot know whether the key was missing or empty before. I fixed the common case (no key) and wrote down the empty-object and bare-string cases. Both leave the same working config, which is what the interviewees cared about. |
| R3 | Two different non-empty messages to the same reachable peer should both succeed, and the two replies are different. | Each call returns the reply the peer gave to that message. | Checkability. Whether two replies differ depends on the remote agent, not on our code. A real agent can answer two questions the same way. What users wanted was that the message text never decides success, and that a reply is the one for their message. |
| R4 | When a peer cannot be reached at all, the call must fail quickly with a connection error. | When the peer address refuses connections, the call must fail quickly with a connection error. | Feasibility. An address that silently drops packets makes the TCP connect hang until the operating system gives up, which we do not control. A refused connection fails at once, which is the dead peer case the interviewees described. |
| R5 | A multi-turn conversation must stop at maxTurns. The record still shows turns = 4 with maxTurns = 4. | A conversation stops sending once the count reaches maxTurns, and the peer gets at most ceil(maxTurns / 2) messages. | Feasibility. One ask is a message and a reply, so turns grow by 2. With an odd cap like 3 the count jumps from 2 to 4 because we cannot keep the peer from replying. The inbound side counts the same way. The user need, a conversation that cannot run forever, is still met. |
| R7 | An agent must only accept inbound A2A tasks from peers in its own allowedPeers list; others are rejected before a session is created. | Every inbound task is recorded with the caller's x-a2a-peer name, or its address when no name is sent. | Feasibility and conflict. The x-a2a-peer header is chosen by the caller, so anyone can claim to be "alice" and the check would give a false sense of safety. Real authentication needs shared keys, which is outside this feature. It also conflicts with R6 and with how allowedPeers works, since allowedPeers is the list of peers we call, and B would have to list every agent that calls it even if it never calls them back. The interview worry was not knowing who is asking for files, so the revised version makes the caller visible. |

R6 is kept as written because the plugin already does it and it can be checked as stated.
